# 组织架构 (Org) 1对1扩展实现设计方案

## 1. 现状分析与确立基调
经过查阅 `five_ms` 项目 `bsy-module-system` 的源码，发现 `system_dept` 表设计完善，包含了 `path` (如 100.101.103) 用于递归查询，并已支持多租户 (`TenantBaseDO`)。同时，需要修正一个关键判断：`DeptService` 并不存在可直接复用的“全量组织树缓存”，当前明确暴露出来的是 `getChildDeptIdListFromCache`，它缓存的是某个节点下的子孙部门 ID 集合，而不是完整 `DeptDO` 快照，更不是 `Dept + BizOrgExt` 的联合快照。

**结论**：完全沿用《架构决策记录》中推荐的**Option C (1:1 主从表扩展模式)**。但需要进一步收敛为：写路径黑盒复用 `DeptService`，读路径由 `biz` 模块自己维护组织快照能力。也就是说，业务侧不重新实现树结构落库规则，但需要自行维护 `Dept + BizOrgExt` join 后的查询快照或查询组装层。

## 2. 数据库设计 (Biz模块)

在 `biz` 模块创建一张新的扩展表，主键与 `system_dept` 保持 1:1：

```sql
CREATE TABLE biz_org_extension (
    dept_id BIGINT PRIMARY KEY,    -- 强关联 system_dept.id
    org_type VARCHAR(32) NOT NULL, -- 组织类型: SCHOOL, COLLEGE, MAJOR, CLASS...
    biz_line VARCHAR(32),          -- 业务线: TEACHING, REGULAR
    lifecycle_status VARCHAR(32),  -- 生命周期: PREPARING, RUNNING, GRADUATED
    
    -- 核心：利用 JSONB / JSON 将多态特有属性拍平，避免列膨胀
    attributes JSONB,              
    
    creator VARCHAR(64),
    create_time DATETIME,
    updater VARCHAR(64),
    update_time DATETIME,
    deleted BIT,
    tenant_id BIGINT
) COMMENT '业务组织架构扩展表';
```

## 3. 核心代码结构设计

### 3.1 持久化映射与多态 DO
```java
@TableName(value = "biz_org_extension", autoResultMap = true)
@Data
public class BizOrgExtRecord extends TenantBaseDO {
    @TableId(type = IdType.INPUT)
    private Long deptId;
    
    private String orgType;
    private String bizLine;
    private String lifecycleStatus;
    
    // MyBatis-Plus JSON 映射
    @TableField(typeHandler = JacksonTypeHandler.class)

public abstract class BizOrgExtDO {
    private Long deptId;
    private OrgType orgType;
    private BizLine bizLine;
    private OrgLifecycleStatus lifecycleStatus;
}

public class ClassBizOrgExtDO extends BizOrgExtDO {
    private String grade;
    private String eduLevel;
}
```

## 4. 方案的无敌之处
1. **0 侵入性**：不需要修改 `five_ms/bsy-module-system` 中 `DeptService` 和 `DeptDO` 的一二代码，脚手架依然可以无痛升级。
2. **数据权限天然适配**：既然底层生成的依然是标准的 `DeptDO` 并在 `system_dept` 里存在，那么系统配置“角色-部门”数据权限时可以直接勾选，底层框架自带的 MyBatis 拦截器（或AOP）对数据权限的处理依然能够完美生效。
3. **DO 也保持强类型多态**：对外 DTO 多态只是表层优雅，内部缓存与业务逻辑同样可以围绕 `ClassBizOrgExtDO` 这类强类型对象展开，不必长期忍受 `Map<String, Object>` 的弱类型蔓延。
4. **缓存边界清晰**：既然 `DeptService` 只缓存子孙 ID，那么 Org 查询缓存就应由 `biz` 模块独立承担，避免出现“system 缓一半、biz 查一半”的暧昧结构。
