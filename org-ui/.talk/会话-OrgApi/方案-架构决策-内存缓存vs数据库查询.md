# 架构决策记录 (ADR)：组织架构查询方案选型

## 1. 方案对比：Java 内存全量缓存 vs PostgreSQL 复杂查询

在面对组织架构这种**读极多、写极少、强层级关系、数据量有限**的业务场景时，我们有两条截然不同的技术路线：

### 路线 A：基于 PostgreSQL (Ltree + Jsonb) 数据库计算
- **核心思想**：将过滤、递归、数据权限交集全部下推到数据库层面完成。
- **优点**：
  - 天然的数据一致性，毫无集群状态同步烦恼。
  - 充分利用了 PG 的高级特性，SQL 极度精简优雅。
  - 无论数据膨胀到多少，都能保持稳定（GIST / GIN 索引）。
- **缺点**：
  - 深度绑定了 PostgreSQL，若未来有信创需求替换为 MySQL 或 Oracle 将面临巨大重构代价。
  - 数据库并发连接数是瓶颈，面对高频的“查询树”请求（如每次登录都要渲染树），DB 压力较大。
  - 树形拼装仍需要在 Java 中做 O(N) 的后处理。

### 路线 B：Java 本地内存全量缓存 (Local Cache + Pub/Sub)
- **核心思想**：应用启动或定时/按需将整棵组织树（扁平列表 + 引用关系）加载进 JVM 内存，所有查询、过滤、权限计算全部在 Java 内存中通过 Stream API 极速完成。
- **数据量可行性分析**：
  - 一所大型高校：1个学校 + 50个学院 + 200个专业 + 4年*200个班级 = 约 2000~5000 个节点。
  - 即便是百万级节点的集团企业，在 Java 内存中也仅占约 100~300 MB，完全可控。
- **优点**：
  - **极致的性能**：内存中指针遍历，响应时间在微秒级，完全解放数据库。
  - **数据库无关**：底层表只需要简单的 `id, parent_id` 即可，不用引入 `ltree`，兼容任何关系型数据库（MySQL, PG, Oracle）。
  - **极其灵活的复杂查询**：Java 中做多维度 JSON 属性过滤、Bottom-Up 的树裁剪、数据权限求交集，比写复杂 SQL 简单且易于单测。
- **缺点（及解决手段）**：
  - **集群一致性问题**：当节点 A 修改了组织架构，节点 B 的本地缓存还是旧的。
    - *解决手段*：引入 Redis Pub/Sub（发布订阅）机制。任何对组织的写操作（增删改），在落库后，向 Redis 发布一条 `ORG_TREE_CHANGED` 消息。集群内所有节点订阅该消息，收到后异步重新加载一次全量树覆盖本地缓存。由于写操作极低频，这种刷新代价完全可以忽略。

## 2. 结论建议 (Recommendation)

我**强烈推荐采用【路线 B：Java 内存全量缓存】**。

**理由如下：**
1. **解耦与普适性**：您的项目可能在未来面临不同客户的数据库环境差异。不强依赖 Postgres 的 `ltree` 会让系统拥有更好的商业化交付能力。
2. **性能数量级的碾压**：鉴于场景 1 是“加载组织树”，场景 2 是“高频作为下游接口的入参计算”，这两者对并发和响应时间要求极高。放在 JVM 内存中是降维打击。
3. **一致性极易解决**：引入 Redis Pub/Sub 同步刷新本地缓存（如 Caffeine 或者简单的 `AtomicReference<Map>`），工程实现非常成熟且简单（几十行代码即可实现）。

## 3. 推荐架构实现 (路线 B)
- **存储层**：普通的 `organization` 表，无须 ltree，保留 jsonb 或退化为 varchar(json) 均可。
- **缓存组件**：利用 Spring Cache + Caffeine 作为本地缓存。
- **刷新机制**：利用 Redis `MessageListener`。当 `POST/PUT/DELETE /organizations` 被调用时：
  1. 更新数据库。
  2. `redisTemplate.convertAndSend("channel:org_sync", "refresh");`
- **查询服务层**：
  - `OrgCacheManager.getAllOrgs()` -> 返回内存中的 `List<OrgDTO>`（带父子引用）。
  - 对这棵内存树使用递归和 Java Stream 进行权限裁剪和属性过滤。
