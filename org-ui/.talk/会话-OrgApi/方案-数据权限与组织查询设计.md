# 组织架构：数据权限与查询方案设计 (Service & Data Layer)

## 1. 核心业务挑战分析
在组织架构查询中，主要的挑战在于：
1. **树形结构的关联查询**：前端需要一棵完整的树，如果我们按照特定属性（如班级的 `grade=2026`）过滤，那么仅命中叶子节点。我们必须把该叶子节点到根节点的所有父节点（专业、学院、学校）都一同查出。
2. **PostgreSQL JSONB + Ltree 特性利用**：借助 PgSQL 强大的 `ltree`（用于高效树形查询）和 `jsonb`（用于多态扩展属性查询），可以抛弃繁杂的 `LIKE '%/id/%'` 或者在应用层做递归遍历。
3. **数据权限隔离的宽与严**：
   - **场景1（宽，展示用）**：只为“降噪”，查出匹配的节点并补全其父链路即可。
   - **场景2（严，数据流转用）**：计算严格的 `orgId` 集合透传给下游系统（如学生查询）。

## 2. 数据库设计 (PostgreSQL)

首先，开启 `ltree` 扩展：
```sql
CREATE EXTENSION IF NOT EXISTS ltree;
```

表结构关键字段设计：
```sql
CREATE TABLE organization (
    id VARCHAR(64) PRIMARY KEY,       -- 雪花算法ID，纯数字字符串（ltree的label只支持字母数字下划线）
    parent_id VARCHAR(64),
    name VARCHAR(128),
    type VARCHAR(32),                 -- SCHOOL, COLLEGE, CLASS 等
    
    path ltree,                       -- ltree路径，例如 '1.10.100.1000'
    attributes jsonb,                 -- 扩展属性，例如 '{"grade": "2026", "eduLevel": "本科"}'
    
    -- 其他常规字段...
);

-- 创建索引以极大加速查询
CREATE INDEX idx_org_path ON organization USING GIST (path);
CREATE INDEX idx_org_attributes ON organization USING GIN (attributes);
```

### MyBatis-Plus 实体映射
```java
@Data
@TableName(value = "organization", autoResultMap = true)
public class OrganizationEntity {
```

## 3. 数据权限上下文 (DataScopeContext)

定义一个上下文对象来承载当前管理员对组织的数据权限：
```java
@Data
public class DataScopeContext {
    // 具有递归权限的节点ID集合 (可见其下所有子孙节点)
    private List<String> recursiveOrgIds;    
    
    // 仅具有当前节点权限的ID集合 (只可见该节点本身)
    private List<String> nonRecursiveOrgIds; 
}
```

## 4. 场景一：组织树展示（松散权限、补全父链路）

**业务逻辑：** 找到既符合“过滤条件”（例如 `grade=2026`，`name=计算机`），又在“管理员权限”范围内的节点。随后，通过 PgSQL 把这些命中节点的所有**祖先节点**一并查出返回给前端，从而在应用层构建出一棵连贯的树。

**PostgreSQL CTE 优雅实现：**
我们在 Mapper.xml 或通过 `@Select` 编写如下 SQL（结合 MyBatis 动态标签）：

```sql
WITH matched_nodes AS (
    SELECT id, path 
    FROM organization
    WHERE 
        -- 1. 数据权限隔离 (宽松过滤：命中这些范围内的任意节点即可)
        (
            -- 递归权限：path 是授权节点路径的后代
            path <@ ANY (ARRAY[#{recursivePaths}]::ltree[])
            OR 
            -- 非递归权限：直接匹配ID
            id IN (#{nonRecursiveIds})
        )
        -- 2. 业务筛选条件 (动态拼接)
        <if test="query.keyword != null">
            AND name LIKE CONCAT('%', #{query.keyword}, '%')
        </if>
        <if test="query.attributes != null">
            -- 利用 JSONB @> 包含操作符进行特有属性匹配 (如班级的 grade)
            AND attributes @> cast(#{jsonAttrsStr} as jsonb)
        </if>
)
-- 3. 补全祖先链路
-- 利用 string_to_array(text(path), '.') 将路径如 '1.2.3' 拆解为行 [1, 2, 3]
SELECT * 
FROM organization
WHERE id IN (
    SELECT unnest(string_to_array(text(path), '.')) 
    FROM matched_nodes
);
```

**Service层组装逻辑：**
取出上面的平铺列表后，在 Java 内存中通过 `Map<String, List<Organization>>` 以 O(N) 的时间复杂度组装成前端需要的树形结构即可。此方式极其高效，只需一次数据库 IO，规避了大量重复的父节点拉取。

## 5. 场景二：作为下游查询参数（严格数据权限）

**业务逻辑：** 该场景不需要组装树，也不需要查出无关的父节点，只需要严格过滤出用户实际拥有权限并且符合筛选条件的叶子节点/目标节点 ID 集合。

**实现思路：**
此场景下，我们可以直接使用 MyBatis-Plus 的 `QueryWrapper`，或者只执行上面 CTE 中的 `matched_nodes` 部分，只选出 `id`。

```java
public List<String> getStrictAuthorizedOrgIds(OrganizationQuery query, DataScopeContext dataScope) {
    // 使用 MyBatis-Plus 的 lambda 链式或者直接写 SQL
    // 伪代码:
    // SELECT id FROM organization 
    // WHERE (权限条件) AND (业务过滤条件)
    
    return baseMapper.selectStrictIds(query, dataScope);
}
```
**底层 SQL 示例：**
```sql
SELECT id 
FROM organization
WHERE 
    (path <@ ANY (ARRAY[#{recursivePaths}]::ltree[]) OR id IN (#{nonRecursiveIds}))
    -- JSONB 匹配
    AND attributes @> cast('{"grade": "2026", "eduLevel": "本科"}' as jsonb)
```

## 6. 设计总结

1. **解决“多层级筛选”的疑惑**：利用 `jsonb` 的 `@>`（包含）操作符，将多层级的特有属性（如只有班级才有的 `grade`）拍平为查询条件。在匹配出目标叶子节点后，利用 PgSQL 的 `path` 拆解（`unnest`）反向捞出父节点。这优雅地解决了“由于父级没有该属性而导致整棵树断裂”的问题。
2. **发挥 PostgreSQL 的威力**：基于 `ltree` 索引（GIST）和 `jsonb` 索引（GIN），使得这类递归查询和 JSON 筛选的性能远超传统的 MySQL `LIKE` 和 `JOIN`。
3. **数据权限宽严相济**：树形展示（场景1）采取“捞取命中点 + 捞出所有父级”的宽容度策略；下游传参（场景2）直接将查询切断在“严格交集”内，做到了架构上各司其职。
