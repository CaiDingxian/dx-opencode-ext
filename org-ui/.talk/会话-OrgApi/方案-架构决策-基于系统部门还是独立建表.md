# 架构决策记录 (ADR)：业务组织架构 (Org) 与底层系统部门 (Dept) 的关系设计

## 1. 业务冲突与背景
目前的后台脚手架/框架 `system` 模块中已经拥有了 `system_dept` 表，负责基础的部门树状结构，且**底层的系统数据权限控制（Data Scope）是强依赖于此表的**。

现在我们需要开发包含学校、学院、专业、班级、教学/行政业务线，且带有定制生命周期（如已毕业）和扩展属性（培养层次、年级）的 `Org` 业务功能。

我们面临三个选择：在原有 `system_dept` 表直接加字段（侵入修改）、完全独立建一套 `biz_org` 表（双树并行）、或者采用“1对1扩展表”的模式。

## 2. 方案对比

### 方案 A：完全独立建表 `biz_organization`（双树并行）
- **做法**：不管 `system_dept`，完全新建一张包含父子级、路径等字段的业务组织表。人员的业务归属存在新表。
- **优点**：业务与底层框架极致解耦，业务怎么改都不影响底座。
- **致命缺点**：数据权限体系破裂！底层的 Data Scope 注解/拦截器是基于 `system_dept` 和 `sys_user_role_dept` 运算的。如果业务组织独立建表，您将不得不重写一整套复杂的数据权限拦截与计算引擎，且在系统中配置权限时，管理员会看到两套树（部门树、组织树），认知极其割裂。

### 方案 B：直接侵入扩展 `system_dept` 表（粗暴加列）
- **做法**：通过 `ALTER TABLE system_dept`，加入 `org_type`, `biz_line`, `lifecycle_status`, `attributes(jsonb)` 等业务特有字段。
- **优点**：开发最快，单表查询极度简单。数据权限机制天然无缝对接。
- **缺点**：严重污染了底层框架的领域模型。`system_dept` 本是一个纯技术/管理的模型（包含 `leader`, `phone`, `email` 等），强行塞入“培养层次”、“已毕业”等纯教务业务属性，会导致日后升级底层脚手架框架变得极其困难。

### 方案 C：1对1扩展表（主从表模型） —— **强烈推荐**
- **做法**：
  - **主体树形结构保留在 `system_dept`**：树的父子关系、名称、排序、基础状态（启/停），统统由底座表接管。底层框架的数据权限完全基于这棵树。
  - **新建一张业务副表 `biz_org_extension`**：
    ```sql
    CREATE TABLE biz_org_extension (
        dept_id BIGINT PRIMARY KEY,  -- 与 system_dept.id 1:1 映射
        org_type VARCHAR(32),        -- SCHOOL, COLLEGE, CLASS...
        biz_line VARCHAR(32),        -- TEACHING, REGULAR...
        lifecycle_status VARCHAR(32),-- RUNNING, GRADUATED...
        attributes JSONB             -- 培养层次、年级等业务多态特有字段
    );
    ```
  - **业务操作**：在调用我们的 `/api/v1/organizations` 新增班级时，Service 层开启事务：先向 `system_dept` 插入一条数据获取 `id`，紧接着将业务特有属性插入 `biz_org_extension` 表中。

## 3. 为什么方案 C 是最优解？

1. **复用了强大的数据权限引擎**：既然框架的 Data Scope 强依赖于 `system_dept`，那么我们就将错就错，顺水推舟。把“班级”、“专业”在底层伪装成一个普通的 Dept。管理员配置数据权限时，勾选的是 `system_dept` 的节点，底层拦截器毫无违和感。
2. **避免了框架污染**：`system_dept` 表结构干干净净，随时可以平滑升级脚手架。所有的业务多态字段全部收敛在 `biz_org_extension` 表中。
3. **完美契合“内存全量缓存”架构**：我们在 Java 层面，启动时做一次 `SELECT d.*, e.* FROM system_dept d LEFT JOIN biz_org_extension e ON d.id = e.dept_id`，将两张表的数据在内存中组装成完整的 `OrganizationDTO` 树。此后，所有的高频查询、过滤、交集计算都在内存中完成，不仅性能极高，而且屏蔽了底层分表的复杂性！

**最终结论：绝不建议另起炉灶建立完全独立的包含父子层级的 `org` 树表，否则数据权限机制将面临重构深渊。采用 `system_dept` 主表管层级 + `biz_org_extension` 附表管业务属性的 1:1 设计，是平衡优雅与框架限制的架构大师之选。**
