# 评价周期·学年·学期 建模设计方案

## 1. 设计原则

### 核心洞察：三层分离

```
┌─────────────────────────────────────────────────────┐
│  时间维度层 (Time Dimension)                         │
│  学年 → 学期    客观日历事实，与业务逻辑无关            │
├─────────────────────────────────────────────────────┤
│  方案配置层 (Scheme Configuration)                    │
│  方案 → 评价模式 + 阶段参与规则    业务规则定义         │
├─────────────────────────────────────────────────────┤
│  业务实例层 (Business Instance)                       │
│  评价周期 = 方案 × 时间    运行时实体                  │
└─────────────────────────────────────────────────────┘
```

### 关键设计决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | **学期是最小粒度的数据锚点** | 活动、行为等业务数据始终按学期录入，无论评价粒度如何 |
| 2 | **评价周期不自行定义时间范围** | 它通过引用学年/学期获得时间属性，避免数据冗余和不一致 |
| 3 | **评价周期是方案在时间轴上的实例化** | 方案是"类"，评价周期是"实例"，天然的模板-实例关系 |
| 4 | **评价模式是方案级配置** | 不同方案可以有不同的评价粒度，提供最大灵活性 |

### 2.2 时间维度：学年 & 学期

```sql
-- ==========================================
-- 学年 (Academic Year)
-- 时间维度的上层容器
-- ==========================================
CREATE TABLE academic_year (
    id              BIGINT PRIMARY KEY,
    school_id       BIGINT       NOT NULL,
    code            VARCHAR(20)  NOT NULL,  -- "2024-2025"
    name            VARCHAR(50)  NOT NULL,  -- "2024-2025学年"
    start_date      DATE         NOT NULL,
    end_date        DATE         NOT NULL,
    is_current      BOOLEAN      DEFAULT FALSE,
    UNIQUE (school_id, code)
);

-- ==========================================
-- 学期 (Semester / Term)
-- 不可分割的原子时间单元，所有业务数据的锚点
-- ==========================================
CREATE TABLE semester (
    id                BIGINT PRIMARY KEY,
    academic_year_id  BIGINT      NOT NULL REFERENCES academic_year(id),
    term_no           SMALLINT    NOT NULL,  -- 1=第一学期, 2=第二学期
    name              VARCHAR(50) NOT NULL,  -- "2024-2025学年第一学期"
    start_date        DATE        NOT NULL,
    end_date          DATE        NOT NULL,
    UNIQUE (academic_year_id, term_no)
);
```

**设计要点**：
- `学年` 和 `学期` 是纯粹的时间维度数据，不包含任何业务逻辑
- `学期` 是系统中最小的时间原子——所有活动、行为、考勤等数据都锚定在学期上
- `term_no` 使用数字而非枚举，保持对未来扩展的开放性（虽然高校通常只有两学期）
- 两者是简单的 **1:N 包含关系**

### 2.3 评价方案 (Evaluation Scheme)

```sql
-- ==========================================
-- 评价方案
-- 定义"怎么评"：评价模式、适用范围、指标体系
-- ==========================================
CREATE TABLE evaluation_scheme (
    id                    BIGINT PRIMARY KEY,
    school_id             BIGINT       NOT NULL,
    name                  VARCHAR(100) NOT NULL,
    
    -- ★ 评价模式 ★
    -- PER_SEMESTER:      按学期评价，每学期独立出结果
    -- PER_ACADEMIC_YEAR: 按学年评价，学年末统一出结果
    -- HYBRID:            数据按学期录入并产出中间分，学年末跨学期总评
    evaluation_mode       VARCHAR(30)  NOT NULL,
    
    -- 适用范围
    cohort_year_from      SMALLINT,            -- 适用起始入学年份（含），如 2023
    cohort_year_to        SMALLINT,            -- 适用结束入学年份（含），NULL=不限
    edu_level             VARCHAR(20),         -- 培养层次: COLLEGE/BACHELOR/UPGRADED
    program_duration      SMALLINT NOT NULL,   -- 学制年限: 2/3/4
    
    status                VARCHAR(20) DEFAULT 'ACTIVE',
    
    CONSTRAINT chk_eval_mode CHECK (
        evaluation_mode IN ('PER_SEMESTER', 'PER_ACADEMIC_YEAR', 'HYBRID')
    )
);
```

**三种评价模式详解**：

| 模式 | 数据录入粒度 | 评价出分粒度 | 典型场景 |
|------|-------------|-------------|---------|
| `PER_SEMESTER` | 学期 | 学期 | 每学期独立评价，互不影响 |
| `PER_ACADEMIC_YEAR` | 学期 | 学年 | 数据按学期录入，学年末统一评价 |
| `HYBRID` | 学期 | 学期 + 学年 | 每学期先出中间分，学年末做跨学期总评 |

> **关于 HYBRID 模式**：这正是需求中"活动和行为按学期记录，但总评要按学年总评"的场景。
> 系统会为每学期生成 `SEMESTER` 类型的评价周期（中间评分），同时在学年末生成
> `ACADEMIC_YEAR` 类型的评价周期（最终总评）。跨学期关联规则（如"一学期有负面记录则全年0分"）
> 在学年级评价周期的计算逻辑中执行。

### 2.4 阶段参与规则 (Stage Participation Rule)

```sql
-- ==========================================
-- 方案的年级/学期参与规则
-- 控制哪些阶段的学生参与评价
-- ==========================================
CREATE TABLE scheme_stage_rule (
    id            BIGINT PRIMARY KEY,
    scheme_id     BIGINT   NOT NULL REFERENCES evaluation_scheme(id),
    grade_level   SMALLINT NOT NULL,    -- 年级序号: 1=大一, 2=大二, 3=大三, 4=大四
    term_no       SMALLINT,             -- 学期: NULL=整个学年, 1=仅上学期, 2=仅下学期
    participate   BOOLEAN  NOT NULL DEFAULT TRUE,
    remark        VARCHAR(200),
    UNIQUE (scheme_id, grade_level, term_no)
);
```

**配置示例**（本科4年制方案）：

| grade_level | term_no | participate | 含义 |
|:-----------:|:-------:|:-----------:|------|
| 1 | NULL | false | 大一全年不参与 |
| 2 | NULL | true  | 大二全年参与 |
| 3 | NULL | true  | 大三全年参与 |
| 4 | 1    | true  | 大四上学期参与 |
| 4 | 2    | false | 大四下学期不参与（实习期） |

> **年级计算方式**：`grade_level = 当前学年起始年份 - 学生入学年份 + 1`
> 
> 例：学生2022年入学，当前学年为2024-2025，则 grade_level = 2024 - 2022 + 1 = 3（大三）

### 2.5 评价周期 (Evaluation Period) ★ 核心

```sql
-- ==========================================
-- 评价周期
-- 方案在时间轴上的实例化，是评价流程的执行载体
-- ==========================================
CREATE TABLE evaluation_period (
    id                BIGINT PRIMARY KEY,
    scheme_id         BIGINT      NOT NULL REFERENCES evaluation_scheme(id),
    academic_year_id  BIGINT      NOT NULL REFERENCES academic_year(id),
    
    -- ★ 核心设计：通过 semester_id 的有无区分粒度 ★
    -- semester_id IS NOT NULL → 学期级周期
    -- semester_id IS NULL     → 学年级周期
    semester_id       BIGINT      REFERENCES semester(id),
    
    -- 冗余字段，与 semester_id 是否为空对应，便于查询和理解
    period_type       VARCHAR(20) NOT NULL,  -- 'SEMESTER' | 'ACADEMIC_YEAR'
    
    -- 业务状态
    status            VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    -- PENDING     → 未开始
    -- DATA_ENTRY  → 数据录入中
    -- EVALUATING  → 评审中
    -- COMPLETED   → 已完成
    -- LOCKED      → 已锁定（归档，不可修改）
    
    name              VARCHAR(100),
    
    CONSTRAINT chk_period_type CHECK (
        (period_type = 'SEMESTER'      AND semester_id IS NOT NULL) OR
        (period_type = 'ACADEMIC_YEAR' AND semester_id IS NULL)
    ),
    -- 同一方案、同一学年、同一学期（或学年级）不能重复
    UNIQUE (scheme_id, academic_year_id, semester_id)
);
```

**这是整个设计的核心**。评价周期的优雅之处在于：

1. **它不自行维护时间范围**——通过 `academic_year_id` + `semester_id` 引用时间维度，天然与日历数据保持一致
2. **粒度由一个 nullable FK 决定**——`semester_id` 为空则学年级，非空则学期级，简洁清晰
3. **它是方案的运行实例**——`scheme_id` 关联方案，携带方案的评价规则
4. **它是流程的载体**——`status` 驱动评价业务流程

## 3. 不同评价模式下的周期生成

### 3.1 PER_SEMESTER 模式

```
学年: 2024-2025
├── EvaluationPeriod(type=SEMESTER, semester=第一学期, scheme=A)  ← 独立评价
└── EvaluationPeriod(type=SEMESTER, semester=第二学期, scheme=A)  ← 独立评价
```

每学期独立产出评价结果，互不干扰。

### 3.2 PER_ACADEMIC_YEAR 模式

```
学年: 2024-2025
└── EvaluationPeriod(type=ACADEMIC_YEAR, semester=NULL, scheme=B) ← 学年末统一评价
```

学年末一次性评价，从两个学期的数据中聚合。

### 3.3 HYBRID 模式

```
学年: 2024-2025
├── EvaluationPeriod(type=SEMESTER, semester=第一学期, scheme=C)  ← 中间评分
├── EvaluationPeriod(type=SEMESTER, semester=第二学期, scheme=C)  ← 中间评分
└── EvaluationPeriod(type=ACADEMIC_YEAR, semester=NULL, scheme=C) ← 学年总评
```

同一方案下同一学年共存 **3个评价周期**：
- 2个学期级周期：产出中间分
- 1个学年级周期：基于两学期中间分 + 跨学期规则，产出最终总评

> 跨学期规则示例："某指标只要有一学期存在负面记录，学年该指标得分为0"——
> 这在学年级周期的评分计算中实现，查询两个学期级周期的中间结果即可。

## 4. 业务数据与评价结果的挂载

```
                     ┌──────────┐
                     │  学期     │
                     │(Semester)│
                     └────┬─────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
     ┌────────────────┐     ┌──────────────────┐
     │  业务数据       │     │  评价周期          │
     │ (Activity,     │     │(EvaluationPeriod) │
     │  Behavior...)  │     │                   │
     │                │     │ period_type =     │
     │ semester_id ───┤     │ SEMESTER 或       │
     │  始终指向学期   │     │ ACADEMIC_YEAR     │
     └────────────────┘     └────────┬──────────┘
                                     │
                                     ▼
                            ┌────────────────┐
                            │  评价结果       │
                            │(EvalResult)    │
                            │                │
                            │ period_id ─────┤
                            │  指向评价周期   │
                            └────────────────┘
```

**规则**：
- **业务数据** → 始终挂在 `semester_id` 上（最细粒度）
- **评价结果** → 挂在 `evaluation_period_id` 上（按配置的粒度）
- 计算评价结果时，系统根据 `period_type` 决定聚合范围：
  - `SEMESTER` → 只取对应学期的数据
  - `ACADEMIC_YEAR` → 取该学年下所有学期的数据

## 5. 学年阶段判定逻辑

### 5.1 年级推算

```
grade_level = academic_year.start_year - student.enrollment_year + 1
```

### 5.2 阶段判定矩阵

以本科（4年制）为例：

| grade_level | 含义 | term_no=1 | term_no=2 |
|:-----------:|------|-----------|-----------|
| 1 | 大一（新生年级） | 大一上 | 大一下 |
| 2 | 大二 | 大二上 | 大二下 |
| 3 | 大三 | 大三上 | 大三下 |
| 4 | 大四（毕业年级） | 大四上 | 大四下（实习期） |

以专科（3年制）为例：

| grade_level | 含义 | term_no=1 | term_no=2 |
|:-----------:|------|-----------|-----------|
| 1 | 大一 | 大一上 | 大一下 |
| 2 | 大二 | 大二上 | 大二下 |
| 3 | 大三（毕业年级） | 大三上 | 大三下（实习期） |

> **毕业年级** = `grade_level == program_duration`（方案中配置的学制年限）
> **实习期** = 毕业年级的第二学期，即 `grade_level == program_duration AND term_no == 2`

### 5.3 参与判定伪代码

```python
def should_participate(student, scheme, academic_year, semester):
    """判断学生在某学期是否参与评价"""
    grade = academic_year.start_year - student.enrollment_year + 1
    
    # 超出学制范围（已毕业/延期等异常情况）
    if grade < 1 or grade > scheme.program_duration:
        return False
    
    # 查找精确匹配的规则（指定学期）
    rule = find_rule(scheme, grade, semester.term_no)
    if rule:
        return rule.participate
    
    # 查找年级级别的规则（term_no = NULL）
    rule = find_rule(scheme, grade, None)
    if rule:
        return rule.participate
    
    # 无规则 → 默认参与
    return True
```

## 6. 完整场景推演

### 场景：某高校的 HYBRID 模式

**背景**：
- 学校有方案C：本科4年制，HYBRID模式
- 大一不参与，大四下学期不参与
- 2024-2025学年，学生张三（2023年入学，大二）

**系统行为**：

```
1. 学年日历已建立：
   academic_year: 2024-2025
   ├── semester: 第一学期 (2024-09 ~ 2025-01)
   └── semester: 第二学期 (2025-02 ~ 2025-07)

2. 系统为方案C生成评价周期：
   ├── period_1: type=SEMESTER,      semester=第一学期, status=PENDING
   ├── period_2: type=SEMESTER,      semester=第二学期, status=PENDING
   └── period_3: type=ACADEMIC_YEAR, semester=NULL,     status=PENDING

3. 张三 grade_level = 2024 - 2023 + 1 = 2（大二）
   → 查阶段规则 → 大二参与 ✓

4. 第一学期结束：
   → period_1 进入评审 → 产出张三的学期中间分
   → 张三本学期有一条负面行为记录

5. 第二学期结束：
   → period_2 进入评审 → 产出张三的学期中间分

6. 学年末，period_3 进入评审：
   → 聚合 period_1 + period_2 的中间分
   → 应用跨学期规则："指标X，一学期有负面记录则全年0分"
   → 张三第一学期有负面记录 → 指标X学年得分 = 0
   → 产出学年总评结果
```

## 7. 设计优势总结

| 特性 | 说明 |
|------|------|
| **概念清晰** | 时间维度、方案配置、业务实例三层分离，职责明确 |
| **数据一致** | 评价周期不冗余时间信息，引用时间维度确保一致性 |
| **灵活配置** | 三种评价模式覆盖所有需求场景，方案级别独立配置 |
| **粒度统一** | 业务数据始终挂在学期上，评价结果挂在周期上，锚点明确 |
| **规则可扩展** | 阶段参与规则、跨学期关联规则在业务层实现，模型不耦合 |
| **查询友好** | 通过 `period_type` + `semester_id` 的有无，清晰区分粒度 |
