# 评价周期建模设计 V2 —— 融合方案

> 本文档是对 V1 方案的迭代，基于核心洞察：**在素质评价系统中，"学期"本质上就是评价周期本身**，无需作为独立的时间维度实体存在。

## 1. V1 方案的反思

V1 中有三个时间相关实体：

```
academic_year  →  semester  ←──  evaluation_period
   (学年)          (学期)           (评价周期)
```

问题在于：
- `semester` 在本系统中**没有独立于评价的业务含义**（这不是教务系统，不需要排课/考试）
- `semester` 硬编码了"一学年=两学期"的假设，不支持季度制等变体
- `evaluation_period` 又要通过 nullable FK 去引用 `semester`，出现了概念上的"中间层冗余"

**用户洞察**：既然业务数据最终都是为评价服务的，为何不让学校直接定义"每年几个评价周期"，把学期和评价周期合而为一？

## 2. 核心设计思路

### 2.1 两个本质问题

| 问题 | V1 的回答 | V2 的回答 |
|------|----------|----------|
| 一年分几段？ | 固定2个学期 | 学校自定义 N 个评价周期 |
| 数据挂在哪里？ | 挂在学期上 | 挂在评价周期上 |

### 2.2 架构简化

```
V1:  academic_year → semester → evaluation_period   (3 层)

V2:  academic_year → eval_period                     (2 层)
```

`eval_period`（评价周期）同时承担两个角色：
1. **时间容器** —— 定义时间范围，业务数据锚定于此
2. **评价载体** —— 管理评价流程的状态生命周期

## 3. 核心模型

### 3.1 ER 关系图

```
                    ┌──────────────┐
                    │   School     │
                    └──────┬───────┘
                           │
             ┌─────────────┼───────────────┐
             │             │               │
             ▼             ▼               ▼
     ┌────────────┐  ┌───────────┐  ┌──────────────────┐
     │AcademicYear│  │EvalPeriod │  │EvaluationScheme  │
     │  (学年)     │  │ (评价周期) │  │  (评价方案)       │
     │            │  │           │  │                  │
     │ id         │←─│ year_id   │  │ id               │
     │ school_id  │  │ period_no │  │ school_id        │
     │ code       │  │ scope     │  │ periods_per_year │
     │ name       │  │ name      │  │ annual_summary   │
     └────────────┘  │ start/end │  └────────┬─────────┘
                     │ status    │           │
                     └─────┬─────┘  ┌────────┴─────────┐
                           │        │                  │
           ┌───────────────┤        ▼                  ▼
           │               │  ┌────────────────┐
           ▼               ▼  │SchemeStageRule  │
  ┌──────────────┐ ┌──────────┐(阶段参与规则)    │
  │ 业务数据      │ │ 评价结果  │                │
  │(活动/行为)   │ │          │ scheme_id      │
  │              │ │student_id│ grade_level    │
  │period_id ────┤ │period_id │ period_no      │
  │ 直接挂周期   │ │scheme_id │ participate    │
  └──────────────┘ └──────────┘└────────────────┘
```

### 3.2 表结构

```sql
-- ==========================================
-- 学年 (Academic Year)
-- 时间容器，不变
-- ==========================================
CREATE TABLE academic_year (
    id              BIGINT PRIMARY KEY,
    school_id       BIGINT       NOT NULL,
    code            VARCHAR(20)  NOT NULL,  -- "2024-2025"
    name            VARCHAR(50)  NOT NULL,  -- "2024-2025学年"
    start_date      DATE         NOT NULL,
    end_date        DATE         NOT NULL,
    is_current      BOOLEAN      DEFAULT FALSE,
    UNIQUE (school_id, code)
);

-- ==========================================
-- 评价周期 (Evaluation Period)
-- ★ 融合了原来的"学期"和"评价周期"两个概念 ★
-- 
-- 职责一：时间切分 —— 学校自定义一年分几段
-- 职责二：评价载体 —— 管理评价流程状态
-- ==========================================
CREATE TABLE eval_period (
    id                BIGINT PRIMARY KEY,
    school_id         BIGINT       NOT NULL,
    academic_year_id  BIGINT       NOT NULL REFERENCES academic_year(id),
    
    -- 周期序号与范围
    period_no         SMALLINT     NOT NULL,  -- 1, 2, 3, ...
    name              VARCHAR(100) NOT NULL,  -- "2024-2025学年 第一学期"
    start_date        DATE         NOT NULL,
    end_date          DATE         NOT NULL,
    
    -- 评价流程状态
    status            VARCHAR(20)  NOT NULL DEFAULT 'PENDING',
    -- PENDING    → 未开始
    -- DATA_ENTRY → 数据录入中
    -- EVALUATING → 评审中
    -- COMPLETED  → 已完成
    -- LOCKED     → 已锁定

    UNIQUE (academic_year_id, period_no)
);
```

### 3.3 评价方案

```sql
CREATE TABLE evaluation_scheme (
    id                    BIGINT PRIMARY KEY,
    school_id             BIGINT       NOT NULL,
    name                  VARCHAR(100) NOT NULL,
    
    -- 适用范围
    cohort_year_from      SMALLINT,            -- 适用起始入学年份
    cohort_year_to        SMALLINT,            -- 适用结束入学年份
    edu_level             VARCHAR(20),         -- COLLEGE / BACHELOR / UPGRADED
    program_duration      SMALLINT NOT NULL,   -- 学制年限: 2/3/4
    
    -- ★ 是否需要学年总评 ★
    -- true:  除各周期评价外，学年末还要做一次跨周期总评
    -- false: 各周期独立评价即可
    annual_summary        BOOLEAN NOT NULL DEFAULT FALSE,
    
    status                VARCHAR(20) DEFAULT 'ACTIVE'
);
```

**关于评价模式的简化**：

V1 用 `evaluation_mode` 区分三种模式。V2 中这变成了两个正交的配置：

| V1 模式 | V2 等价配置 | 说明 |
|---------|-----------|------|
| PER_SEMESTER | 一年2周期 + annual_summary=false | 各周期独立评价 |
| PER_ACADEMIC_YEAR | 一年1周期 + annual_summary=false | 整年一个评价周期 |
| HYBRID | 一年2周期 + annual_summary=true | 各周期评价 + 学年跨周期总评 |

> **额外收益**：还能支持 V1 无法表达的场景，如"一年4周期（季度制）+ 学年总评"。

### 3.4 阶段参与规则

```sql
CREATE TABLE scheme_stage_rule (
    id            BIGINT PRIMARY KEY,
    scheme_id     BIGINT   NOT NULL REFERENCES evaluation_scheme(id),
    grade_level   SMALLINT NOT NULL,    -- 年级: 1=大一, 2=大二, ...
    period_no     SMALLINT,             -- 周期号: NULL=整年, 1/2/...=具体周期
    participate   BOOLEAN  NOT NULL DEFAULT TRUE,
    remark        VARCHAR(200),
    UNIQUE (scheme_id, grade_level, period_no)
);
```

> 注意：V2 中 `term_no` 改为 `period_no`，语义从"第几学期"变为"第几个评价周期"，更通用。

## 4. 学年总评的处理

当方案的 `annual_summary = true` 时，学年末需要跨周期总评。

### 4.1 学年总评不是一个"周期"

**关键认识**：学年总评是对各周期评价结果的**聚合计算**，它不是一个新的"时间段"，也不产生新的业务数据。因此它不应作为 `eval_period` 的一条记录。

### 4.2 学年总评的载体

用一个轻量的结构管理学年总评的生命周期：

```sql
-- ==========================================
-- 学年总评任务（仅当 scheme.annual_summary = true 时存在）
-- 管理跨周期总评的状态和流程
-- ==========================================
CREATE TABLE annual_eval_task (
    id                BIGINT PRIMARY KEY,
    scheme_id         BIGINT NOT NULL REFERENCES evaluation_scheme(id),
    academic_year_id  BIGINT NOT NULL REFERENCES academic_year(id),
    
    status            VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    -- 状态与 eval_period 相同: PENDING / EVALUATING / COMPLETED / LOCKED
    
    UNIQUE (scheme_id, academic_year_id)
);
```

### 4.3 总评计算流程

```
学年 2024-2025, 方案C (annual_summary=true, 一年2周期)

  eval_period_1 (周期1)             eval_period_2 (周期2)
  ┌──────────────────┐             ┌──────────────────┐
  │  活动/行为数据     │             │  活动/行为数据     │
  │  周期评价结果      │             │  周期评价结果      │
  └────────┬─────────┘             └────────┬─────────┘
           │                                │
           └──────────┬─────────────────────┘
                      ▼
            ┌───────────────────┐
            │ annual_eval_task  │
            │                   │
            │ 跨周期聚合规则：    │
            │ • 加权平均          │
            │ • 负面记录一票否决   │
            │ • ...              │
            │                   │
            │ → 学年总评结果      │
            └───────────────────┘
```

## 5. 业务数据的挂载

### 5.1 数据归属

```sql
-- 学生活动（直接挂在评价周期上）
CREATE TABLE student_activity (
    id              BIGINT PRIMARY KEY,
    student_id      BIGINT NOT NULL,
    eval_period_id  BIGINT NOT NULL REFERENCES eval_period(id),
    activity_date   DATE,
    -- ...
);

-- 学生行为记录
CREATE TABLE student_behavior (
    id              BIGINT PRIMARY KEY,
    student_id      BIGINT NOT NULL,
    eval_period_id  BIGINT NOT NULL REFERENCES eval_period(id),
    behavior_type   VARCHAR(20) NOT NULL, -- POSITIVE / NEGATIVE
    occur_date      DATE,
    -- ...
);
```

### 5.2 评价结果

```sql
-- 周期级评价结果（每个周期一份）
CREATE TABLE period_eval_result (
    id                BIGINT PRIMARY KEY,
    student_id        BIGINT NOT NULL,
    eval_period_id    BIGINT NOT NULL REFERENCES eval_period(id),
    scheme_id         BIGINT NOT NULL REFERENCES evaluation_scheme(id),
    -- 各指标得分...
    total_score       DECIMAL(6,2),
    UNIQUE (student_id, eval_period_id, scheme_id)
);

-- 学年总评结果（仅 annual_summary=true 时存在）
CREATE TABLE annual_eval_result (
    id                BIGINT PRIMARY KEY,
    student_id        BIGINT NOT NULL,
    academic_year_id  BIGINT NOT NULL REFERENCES academic_year(id),
    scheme_id         BIGINT NOT NULL REFERENCES evaluation_scheme(id),
    -- 各指标得分（聚合后）...
    total_score       DECIMAL(6,2),
    UNIQUE (student_id, academic_year_id, scheme_id)
);
```

## 6. 不同场景的配置对照

### 场景 A：按学期评价（最常见）

```
学校配置：每年 2 个评价周期
方案配置：annual_summary = false

生成的数据结构：
  academic_year: 2024-2025
  ├── eval_period(no=1, "第一学期", 09月~01月)
  └── eval_period(no=2, "第二学期", 02月~07月)

评价结果：
  period_eval_result × 2 (每周期一份)
```

### 场景 B：按学年评价

```
学校配置：每年 1 个评价周期
方案配置：annual_summary = false

生成的数据结构：
  academic_year: 2024-2025
  └── eval_period(no=1, "全年", 09月~07月)

评价结果：
  period_eval_result × 1
```

### 场景 C：学期录入 + 学年总评（HYBRID）

```
学校配置：每年 2 个评价周期
方案配置：annual_summary = true

生成的数据结构：
  academic_year: 2024-2025
  ├── eval_period(no=1, "第一学期", 09月~01月)
  ├── eval_period(no=2, "第二学期", 02月~07月)
  └── annual_eval_task(scheme=C)

评价结果：
  period_eval_result × 2 (各周期中间分)
  annual_eval_result × 1 (学年总评)
```

### 场景 D：季度制（未来扩展）

```
学校配置：每年 4 个评价周期
方案配置：annual_summary = true

生成的数据结构：
  academic_year: 2024-2025
  ├── eval_period(no=1, "Q1", 09月~11月)
  ├── eval_period(no=2, "Q2", 12月~02月)
  ├── eval_period(no=3, "Q3", 03月~05月)
  ├── eval_period(no=4, "Q4", 06月~07月)
  └── annual_eval_task(scheme=D)
```

## 7. V1 vs V2 对比总结

| 维度 | V1（学期+评价周期分离） | V2（融合方案） |
|------|---------------------|--------------|
| **实体数** | 3 个时间相关实体 | 2 个时间相关实体 |
| **灵活性** | 固定2学期/年 | 任意N个周期/年 |
| **概念冗余** | semester 在本系统中无独立业务含义 | 消除冗余，评价周期即时间单元 |
| **年度总评** | nullable FK 区分粒度 | 独立的 annual_eval_task，概念更清晰 |
| **扩展性** | 难以支持季度制等变体 | 天然支持任意时间划分 |
| **数据锚定** | 数据挂在学期上 | 数据挂在评价周期上 |
| **评价模式** | 3个枚举值 (PER_SEMESTER/PER_ACADEMIC_YEAR/HYBRID) | 2个正交配置 (周期数 × 是否总评) |

### V2 的核心优势

1. **概念统一**：评价周期 = 时间单元 = 数据容器 = 评价载体，一个概念贯穿始终
2. **配置正交**：时间划分（几个周期）和评价策略（是否总评）正交组合，比枚举更灵活
3. **年度总评独立**：不再用 nullable FK 混合两种粒度，概念边界更清晰
4. **面向未来**：天然支持季度制等非标准时间划分

## 8. 多方案共用周期的说明

**问题**：`eval_period` 是学校级别的（不关联 scheme），如果同一学校的不同方案需要不同的时间划分怎么办？

**回答**：在中国高校实践中，同一学校的时间划分是统一的（不会出现 A 方案按学期、B 方案按季度）。评价方案的差异在于**评价指标和规则**，而非**时间划分**。

因此 `eval_period` 作为学校级别的共享时间框架是合理的。所有方案共享同一套时间划分，各自独立产出评价结果。

```
                eval_period_1           eval_period_2
                ┌──────────┐            ┌──────────┐
  方案A ────►   │result_A_1│            │result_A_2│
                │          │            │          │
  方案B ────►   │result_B_1│            │result_B_2│
                └──────────┘            └──────────┘
```
