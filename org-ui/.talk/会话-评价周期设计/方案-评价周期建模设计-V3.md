# 评价周期建模设计 V3

> 基于 V2 融合方案的多轮优化迭代。核心变化：语义化主键、去除多租户字段、事件日期内嵌、学历层次独立建模、简化评价模式、全局周期配置。

## 1. V2 → V3 变更总览

| # | 优化点 | V2 | V3 |
|---|--------|----|----|
| 1 | 主键策略 | 数字 `BIGINT` ID | **语义化业务键**（如 `"2025-2026"`, `"2025-2026-1"`） |
| 2 | 租户隔离 | 所有表带 `school_id` | **移除 `school_id`**，非多租户 SaaS |
| 3 | 事件日期 | 仅有周期起止日期 | **周期内嵌 2 组事件时间窗**（行为申报期、公示期） |
| 4 | 学历层次 | `edu_level` + `program_duration` 内嵌于方案 | **`edu_level` 独立字典表**，方案多对多关联 |
| 5 | 评价模式 | 3 种模式（含 HYBRID） | **移除 HYBRID**，仅保留按学期 / 按学年 |
| 6 | 周期数字段 | `period_no SMALLINT` (nullable) | **`periods_per_year` 字段**（值域 `1` / `2`），语义更清晰 |
| 7 | 周期归属 | 概念模糊 | **学年级全局配置** `periods_per_year`，所有方案共用；保留向方案级扩展的路径 |
| 8 | 周期数量约束 | 无约束 | **强制匹配**：`periods_per_year=2` 时每学年必须恰好 2 个周期 |

---

## 2. 语义化主键设计（优化 1）

### 2.1 设计理念

数字 ID 是"地址"，语义键是"名字"。对于学年、评价周期这类有天然标识的实体，语义键同时具备：

- **自然排序**：`"2024-2025"` < `"2025-2026"`，无需 JOIN 即可排序
- **可读性**：日志、调试、API 中直接看到含义
- **去重**：键本身就是唯一约束，无需额外 UNIQUE
- **减少 JOIN**：外键直接是语义值，查询时无需关联主表即可显示名称

### 2.2 键的编码规则

| 实体 | 键格式 | 示例 | 说明 |
|------|--------|------|------|
| 学年 | `{起始年}-{结束年}` | `"2025-2026"` | 自然唯一 |
| 评价周期 | `{学年键}-{周期序号}` | `"2025-2026-1"` | 学年键 + 序号 |
| | | `"2025-2026-0"` | `0` 表示全年单周期 |

> **`-0` 约定**：当 `periods_per_year = 1` 时，周期序号固定为 `0`，表示"整年即周期"。这与 `1`, `2` 的序号区间不重叠，语义清晰。

### 2.3 技术考量

- **类型选择**：`VARCHAR(20)` 足够，且 PostgreSQL 中短字符串做主键性能与 BIGINT 接近
- **不可变性**：学年和周期一旦创建不应修改键值（键即身份）
- **数字 ID 保留**：业务实体（活动、行为等）仍可使用数字 ID 或 UUID，语义键仅用于**时间维度实体**

## 3. 核心模型

### 3.1 ER 关系图

```

          │  academic_year   │
          │  PK: code        │  "2025-2026"
          │  periods_per_year│  全局周期配置
          └──────┬──────────┘
                 │ 1
                 │
                 │ N (强制匹配 periods_per_year)
          ┌──────┴───────┐
          │ eval_period   │

          │  + 公示期      │
          └──────┬───────┘
                 │
        ┌────────┴─────────┐
        ▼                  ▼
   业务数据             评价结果
  (活动/行为)      (period_eval_result)


          ┌──────────────────┐       ┌──────────────┐
          │evaluation_scheme │──M:N──│  edu_level    │
          │  PK: id (BIGINT) │       │  PK: code     │
          │                  │       │  duration     │
          └────────┬─────────┘       └──────────────┘
                   │
                   ▼
          ┌──────────────────┐
          │scheme_stage_rule │
          │  grade_level     │
          │  period_no       │
          └──────────────────┘
```

### 3.2 学年表

```sql
-- ==========================================
-- 学年 (Academic Year)
-- 语义化主键，无 school_id
-- periods_per_year 为全局配置，所有方案共用
-- ==========================================
CREATE TABLE academic_year (
    code              VARCHAR(20)  PRIMARY KEY,   -- "2025-2026"
    name              VARCHAR(50)  NOT NULL,       -- "2025-2026学年"
    start_date        DATE         NOT NULL,
    end_date          DATE         NOT NULL,
    is_current        BOOLEAN      NOT NULL DEFAULT FALSE,

    -- ★ 每年评价周期数（全局配置）★
    -- 1 = 按学年评价（全年一个周期, period_no=0）
    -- 2 = 按学期评价（一年两个周期, period_no=1,2）
    periods_per_year  SMALLINT     NOT NULL DEFAULT 2,

    CONSTRAINT chk_periods_per_year CHECK (periods_per_year IN (1, 2))
);
```

**V2 → V3 变化**：
- `id BIGINT` → `code VARCHAR(20)` 语义化主键
- 移除 `school_id`
- 新增 `periods_per_year`：周期粒度配置从方案级上移到学年级（全局统一）

**设计决策：`periods_per_year` 放在学年表而非方案表**：

当前阶段，全校统一时间划分是最常见的场景。将 `periods_per_year` 放在 `academic_year` 表：
- 学年创建时即确定周期数量，系统自动生成对应数量的 `eval_period`
- 所有方案共用同一套周期，业务数据统一挂载

**未来扩展路径**：若需支持"A 方案按学期、B 方案按学年"，只需：
1. 将 `periods_per_year` 从 `academic_year` 移到 `evaluation_scheme`
2. `eval_period` 新增 `scheme_id` 外键
3. 各方案独立生成各自的周期

> 这是一次表结构的 ALTER，而非架构重设计。语义键、事件日期等设计不受影响。

### 3.3 评价周期表（含事件日期）

```sql
-- ==========================================
-- 评价周期 (Evaluation Period)
-- 融合时间容器 + 评价载体 + 事件日期窗口
-- ==========================================
CREATE TABLE eval_period (
    code              VARCHAR(20)  PRIMARY KEY,   -- "2025-2026-1"
    year_code         VARCHAR(20)  NOT NULL REFERENCES academic_year(code),

    -- 周期基本信息
    period_no         SMALLINT     NOT NULL,       -- 0=全年, 1=第一学期, 2=第二学期
    name              VARCHAR(100) NOT NULL,       -- "2025-2026学年 第一学期"
    start_date        DATE         NOT NULL,
    end_date          DATE         NOT NULL,

    -- ★ 事件日期窗口 ★
    -- 行为申报期：学生提交活动/行为记录的时间窗
    behavior_submit_start   DATE,
    behavior_submit_end     DATE,
    -- 评价公示期：评价结果公示的时间窗
    publicity_start         DATE,
    publicity_end           DATE,

    -- 评价流程状态
    status            VARCHAR(20)  NOT NULL DEFAULT 'PENDING',
    -- PENDING     → 未开始
    -- SUBMITTING  → 申报中（行为申报期内）
    -- EVALUATING  → 评审中（总评计算）
    -- PUBLICITY   → 公示中
    -- COMPLETED   → 已完成
    -- LOCKED      → 已锁定（归档）

    UNIQUE (year_code, period_no)
);
```

**V2 → V3 变化**：
- `id BIGINT` → `code VARCHAR(20)` 语义化主键
- `academic_year_id` → `year_code` 语义化外键
- 移除 `school_id`
- 新增 2 组事件日期窗口（4 个 DATE 字段）：行为申报期、公示期
- 状态枚举细化，与事件日期窗口对应

> **事件日期 vs. 周期日期**：`start_date` / `end_date` 是整个周期的时间范围，事件日期是周期内各业务环节的具体时间窗。事件日期必须在周期日期范围内，且按 `申报 → 评审 → 公示` 的顺序依次进行。

**周期数量约束**：
- 当学年 `periods_per_year = 2` 时，该学年下必须恰好存在 `period_no = 1` 和 `period_no = 2` 两条记录
- 当学年 `periods_per_year = 1` 时，该学年下必须恰好存在 `period_no = 0` 一条记录
- 此约束在应用层强制执行（创建学年时自动生成对应周期）

### 3.4 学历层次表（优化 4）

```sql
-- ==========================================
-- 学历层次 (Education Level)
-- 独立字典表，存储学制年限
-- ==========================================
CREATE TABLE edu_level (
    code              VARCHAR(20)  PRIMARY KEY,   -- "COLLEGE" / "BACHELOR" / "UPGRADED"
    name              VARCHAR(50)  NOT NULL,       -- "专科" / "本科" / "专升本"
    program_duration  SMALLINT     NOT NULL        -- 学制年限: 3 / 4 / 2
);
```

**设计理由**：
- `program_duration` 是学历层次的固有属性，不应放在方案表中
- 同一学历层次的学制全校统一（专科就是 3 年，不会一个方案 3 年另一个 2 年）
- 独立字典表支持未来扩展（如 5 年制本科、硕士研究生等）

### 3.5 评价方案表

```sql
-- ==========================================
-- 评价方案 (Evaluation Scheme)
-- periods_per_year 已移至 academic_year（全局配置）
-- ==========================================
CREATE TABLE evaluation_scheme (
    id                    BIGINT       PRIMARY KEY,
    name                  VARCHAR(100) NOT NULL,

    -- 适用入学年份范围
    cohort_year_from      SMALLINT,               -- 适用起始入学年份（含）
    cohort_year_to        SMALLINT,               -- 适用结束入学年份（含）

    status                VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE'
);
```

**V2 → V3 变化**：
- 移除 `school_id`
- 移除 `edu_level VARCHAR(20)` 和 `program_duration`（拆到独立表 + 关联表）
- 移除 `annual_summary BOOLEAN`（取消 HYBRID 模式后不需要）
- `periods_per_year` 上移到 `academic_year` 表（全局配置）

> **未来扩展**：若需支持不同方案不同粒度，将 `periods_per_year` 从 `academic_year` 移回此表，同时 `eval_period` 加 `scheme_id` 外键即可。

### 3.6 方案 × 学历层次关联表

```sql
-- ==========================================
-- 方案适用的学历层次（多对多）
-- 一个方案可适用于多个学历层次
-- ==========================================
CREATE TABLE scheme_edu_level (
    scheme_id         BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    edu_level_code    VARCHAR(20)  NOT NULL REFERENCES edu_level(code),
    PRIMARY KEY (scheme_id, edu_level_code)
);
```

**典型数据**：

```
方案A（通用方案）:
  scheme_edu_level: (A, COLLEGE), (A, BACHELOR), (A, UPGRADED)

方案B（本科专用方案）:
  scheme_edu_level: (B, BACHELOR)
```

### 3.7 阶段参与规则表

```sql
-- ==========================================
-- 阶段参与规则 (Stage Participation Rule)
-- 控制各年级在各周期是否参与评价
-- ==========================================
CREATE TABLE scheme_stage_rule (
    id            BIGINT       PRIMARY KEY,
    scheme_id     BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    grade_level   SMALLINT     NOT NULL,    -- 年级: 1=大一, 2=大二, ...
    period_no     SMALLINT     NOT NULL,    -- 周期号: 0=全年, 1/2=具体周期
    participate   BOOLEAN      NOT NULL DEFAULT TRUE,
    remark        VARCHAR(200),
    UNIQUE (scheme_id, grade_level, period_no)
);
```

**V2 → V3 变化**：
- `period_no` 不再 nullable，用 `0` 表示全年周期（与 eval_period 的编码规则一致）
- 年级计算公式不变：`grade_level = 当前学年起始年 - 入学年 + 1`

## 4. 移除 HYBRID 模式的分析（优化 5）

### 4.1 原 HYBRID 模式的含义

V2 中 HYBRID = 按学期录入数据 + 学年末跨周期总评。这需要 `annual_summary` 字段和 `annual_eval_task` 表。

### 4.2 为什么移除

用户澄清：实际业务中不存在"先按学期评，再做学年总评"的需求。学校的评价粒度要么是**学期**，要么是**学年**，两者是互斥选择。

- **按学期评价**：每学期独立产出最终评价结果，学年没有汇总
- **按学年评价**：全年只评一次，产出学年级别的最终结果

### 4.3 V3 移除的内容

- `evaluation_scheme.annual_summary` 字段
- `annual_eval_task` 表
- `annual_eval_result` 表
- 场景 C（HYBRID）和场景 D（季度制 + 总评）

### 4.4 periods_per_year 的简化效果

| `periods_per_year` | 含义 | 周期编号 | 评价结果 |
|:---:|------|:---:|------|
| `1` | 按学年评价 | `0` (全年) | 1 份/年 |
| `2` | 按学期评价 | `1`, `2` | 2 份/年 |

> 未来若需支持季度制，只需放开 CHECK 约束允许 `4`，无需结构变更。

## 5. 业务数据挂载

### 5.1 数据归属

```sql
-- 学生活动（直接挂在评价周期上）
CREATE TABLE student_activity (
    id                BIGINT       PRIMARY KEY,
    student_id        BIGINT       NOT NULL,
    eval_period_code  VARCHAR(20)  NOT NULL REFERENCES eval_period(code),
    activity_date     DATE,
    -- ...
);

-- 学生行为记录
CREATE TABLE student_behavior (
    id                BIGINT       PRIMARY KEY,
    student_id        BIGINT       NOT NULL,
    eval_period_code  VARCHAR(20)  NOT NULL REFERENCES eval_period(code),
    behavior_type     VARCHAR(20)  NOT NULL,  -- POSITIVE / NEGATIVE
    occur_date        DATE,
    -- ...
);
```

**语义键的好处**：查询时 `eval_period_code = '2025-2026-1'` 直接可读，无需 JOIN 即可知道"这是2025-2026学年第一学期的数据"。

### 5.2 评价结果

```sql
-- 周期评价结果（每个周期一份）
CREATE TABLE period_eval_result (
    id                BIGINT       PRIMARY KEY,
    student_id        BIGINT       NOT NULL,
    eval_period_code  VARCHAR(20)  NOT NULL REFERENCES eval_period(code),
    scheme_id         BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    -- 各指标得分...
    total_score       DECIMAL(6,2),
    UNIQUE (student_id, eval_period_code, scheme_id)
);
```

**注意**：移除 HYBRID 后不再需要 `annual_eval_result` 表。所有评价结果统一存储在 `period_eval_result` 中。

## 6. 场景配置对照

### 场景 A：按学期评价（最常见）

```
学年配置：periods_per_year = 2
方案适用：scheme_edu_level = [BACHELOR, COLLEGE]

生成的数据结构（创建学年时自动生成）：
  academic_year: "2025-2026" (periods_per_year=2)
  ├── eval_period("2025-2026-1", period_no=1, "第一学期", 09月~01月)
  │   ├── behavior_submit: 12/20 ~ 01/05
  │   └── publicity:       01/11 ~ 01/20
  └── eval_period("2025-2026-2", period_no=2, "第二学期", 02月~07月)
      ├── behavior_submit: 06/15 ~ 06/30
      └── publicity:       07/06 ~ 07/15

评价结果：
  period_eval_result × 2（每学期各一份）
```

### 场景 B：按学年评价

```
学年配置：periods_per_year = 1
方案适用：scheme_edu_level = [BACHELOR]

生成的数据结构：
  academic_year: "2025-2026" (periods_per_year=1)
  └── eval_period("2025-2026-0", period_no=0, "全年", 09月~07月)
      ├── behavior_submit: 06/01 ~ 06/20
      └── publicity:       07/01 ~ 07/15

评价结果：
  period_eval_result × 1
```

### 场景 C：多方案共用周期

```
学年配置：periods_per_year = 2
方案A：适用 [COLLEGE]
方案B：适用 [BACHELOR, UPGRADED]

两个方案共用同一套 eval_period：
  eval_period("2025-2026-1")
  ├── period_eval_result(scheme=A, student=张三/专科)
  └── period_eval_result(scheme=B, student=李四/本科)
```

## 8. V2 → V3 对比总结

| 维度 | V2 | V3 |
|------|----|----|
| **主键策略** | 数字 BIGINT | 语义化 VARCHAR（学年/周期） |
| **租户隔离** | 每表 `school_id` | 无（单租户部署） |
| **时间实体** | 2 表（学年 + 周期） | 2 表，字段更丰富（事件日期、周期数配置） |
| **事件日期** | 无 | 2 组事件时间窗（行为申报期、公示期），驱动状态流转 |
| **学历层次** | 内嵌于方案 | 独立字典表 + 多对多关联 |
| **评价模式** | 3 种（含 HYBRID） | 2 种：`periods_per_year` = 1 或 2 |
| **周期归属** | 概念不明确 | 学年级全局配置，保留向方案级扩展路径 |
| **年度总评** | `annual_summary` + `annual_eval_task` | 移除 |
| **周期编号** | `period_no` nullable | `period_no` NOT NULL, 0=全年 |
| **周期数量** | 无约束 | 强制匹配 `periods_per_year`（应用层校验） |
| **表总数** | 6 表 | 7 表（+edu_level, +scheme_edu_level, -annual_eval_task, -annual_eval_result） |

### V3 核心收益

1. **语义键**：减少 JOIN，查询可读性大幅提升，天然排序
2. **去 school_id**：DDL 更简洁，索引更高效，不引入不必要的多租户复杂性
3. **事件日期内嵌**：行为申报期和公示期可配置，状态机与事件日期联动，支持自动化流转
4. **学历层次解耦**：一个方案可适用多个学历层次，学制年限作为学历的固有属性不再冗余
5. **模式简化**：移除 HYBRID 后，`periods_per_year` 一个字段即可表达所有评价粒度，概念负担最小化
6. **period_no 语义化**：0/1/2 的编码规则统一贯穿周期表和阶段规则表，不再有 NULL 歧义
7. **全局周期 + 扩展性**：当前全校统一配置，未来可低成本迁移到方案级配置
8. **周期数量约束**：创建学年时自动生成匹配数量的周期，杜绝数据不一致

## 9. 完整建表脚本

```sql
-- ========================================
-- V3 完整建表脚本
-- ========================================

-- 1. 学年（含全局周期配置）
CREATE TABLE academic_year (
    code              VARCHAR(20)  PRIMARY KEY,
    name              VARCHAR(50)  NOT NULL,
    start_date        DATE         NOT NULL,
    end_date          DATE         NOT NULL,
    is_current        BOOLEAN      NOT NULL DEFAULT FALSE,
    periods_per_year  SMALLINT     NOT NULL DEFAULT 2,

    CONSTRAINT chk_periods_per_year CHECK (periods_per_year IN (1, 2))
);

-- 2. 评价周期（含事件日期）
CREATE TABLE eval_period (
    code              VARCHAR(20)  PRIMARY KEY,
    year_code         VARCHAR(20)  NOT NULL REFERENCES academic_year(code),
    period_no         SMALLINT     NOT NULL,
    name              VARCHAR(100) NOT NULL,
    start_date        DATE         NOT NULL,
    end_date          DATE         NOT NULL,

    -- 事件日期窗口
    behavior_submit_start   DATE,
    behavior_submit_end     DATE,
    publicity_start         DATE,
    publicity_end           DATE,

    status            VARCHAR(20)  NOT NULL DEFAULT 'PENDING',

    UNIQUE (year_code, period_no)
);

-- 3. 学历层次字典
CREATE TABLE edu_level (
    code              VARCHAR(20)  PRIMARY KEY,
    name              VARCHAR(50)  NOT NULL,
    program_duration  SMALLINT     NOT NULL
);

-- 4. 评价方案
CREATE TABLE evaluation_scheme (
    id                    BIGINT       PRIMARY KEY,
    name                  VARCHAR(100) NOT NULL,
    cohort_year_from      SMALLINT,
    cohort_year_to        SMALLINT,
    status                VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE'
);

-- 5. 方案 × 学历层次
CREATE TABLE scheme_edu_level (
    scheme_id         BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    edu_level_code    VARCHAR(20)  NOT NULL REFERENCES edu_level(code),
    PRIMARY KEY (scheme_id, edu_level_code)
);

-- 6. 阶段参与规则
CREATE TABLE scheme_stage_rule (
    id            BIGINT       PRIMARY KEY,
    scheme_id     BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    grade_level   SMALLINT     NOT NULL,
    period_no     SMALLINT     NOT NULL,
    participate   BOOLEAN      NOT NULL DEFAULT TRUE,
    remark        VARCHAR(200),
    UNIQUE (scheme_id, grade_level, period_no)
);

-- 7. 周期评价结果
CREATE TABLE period_eval_result (
    id                BIGINT       PRIMARY KEY,
    student_id        BIGINT       NOT NULL,
    eval_period_code  VARCHAR(20)  NOT NULL REFERENCES eval_period(code),
    scheme_id         BIGINT       NOT NULL REFERENCES evaluation_scheme(id),
    total_score       DECIMAL(6,2),
    UNIQUE (student_id, eval_period_code, scheme_id)
);

-- ========================================
-- 初始化学历层次字典数据
-- ========================================
INSERT INTO edu_level (code, name, program_duration) VALUES
    ('COLLEGE',   '专科',   3),
    ('BACHELOR',  '本科',   4),
    ('UPGRADED',  '专升本', 2);
```
